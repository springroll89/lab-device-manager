# 实验室设备采集与管理系统 · 设计文档

> 状态：设计（待 Slice A 实现计划）　·　日期：2026-07-01　·　所属：化学/陶瓷膜研发公司（非航空、非 AS9100D）
> 关联：`docs/实验室设备组网方案.md`（硬件拓扑）、`docs/superpowers/specs/2026-06-30-syringe-pump-logger-design.md`（phase-1 采集原型）

---

## 1. 背景与目标

phase-1 做了一个**单台只读采集原型**（本地网页 + CSV），验证了「设备能连、能读、能记」。但实际需要的是一套**全生命周期管理平台**：多设备实时采集 + 结构化落库 + 运行记录/校正/维护台账 + 查询导出 + 异常告警 + 利用率统计。本文档定义这个「真正的系统」。

**核心定位**：SCADA（实时采集/监控）+ LIMS（实验室管理表单）混合。**只读优先**——不依赖电脑端发指令控制设备（phase-2 写控制暂不做）。

## 2. 范围

**In**
- 多设备实时采集、结构化入库（SQLite）。
- 运行记录/采样序列/事件流**自动抓取**；操作人/项目/备注**事后补录**。
- 设备档案、校正台账、维护/故障记录（人工录入表单，接入系统）。
- 实时看板、运行记录查询、导出（CSV/Excel/PDF）、校正/维护管理、维护提醒、飞书告警、利用率统计。

**Out（本期不做）**
- phase-2 写控制（从 app 启停设备、跑校正流程）→ Slice E，带二次确认+审计。
- 给设备下发设定（流速/液量等）——设备设定仍在设备面板完成，app 只读取。

## 4. 总体架构

```
设备(RS485/RS232) ─→ 串口服务器/转换器 ─→ 采集层(复用 phase-1)
                                                 │ InstrumentAdapter / Sampler / StatusSnapshot
                                                 ▼
                                  ┌──── 业务层（新增）────┐
                                  │ RunDetector  (状态转换→开/关 run + 发事件)
                                  │ EventLogger  (事件流，堵车=first-class)
                                  │ Repository   (SQLite 持久化)
                                  │ AlertBot     (飞书 webhook，critical 事件)
                                  │ Maintenance  (提醒规则：工时+日历)
                                  └──────────┬────────────┘
                                             ▼
                          Web UI：实时看板 / 运行查询 / 校正 / 维护 / 导出 / 统计
```
- **采集层复用** phase-1（`pump_monitor/instruments/*`、`sampler.py`、`StatusSnapshot`），不重写。
- **采集层演进**：加 `TcpTransport`（接串口服务器，见组网方案）；多设备并行（一个 transport 挂多个从机地址 + 多个 transport）。
- **新增业务层**：run 检测、事件、持久化、告警、维护——本设计的主体。

## 5. 数据模型（SQLite）

> 标注来源：📡=Modbus 自动读 / ✍️=人工录入 / 🧮=推导

### 5.1 device（设备档案）
| 字段 | 来源 | 说明 |
|---|---|---|
| id, device_type, alias, location, asset_no | ✍️/配置 | PK；类型 pump/stirrer/viscometer |
| model, channels | 📡/✍️ | 型号(TYD02-01 等)、通道数 |
| serial_no, firmware_version | ✍️（待确认寄存器） | 序列号/固件版本 |
| connection, modbus_addr | 配置 | 挂哪条总线/哪个串口服务器口、从机地址（多台并总线时是主键一部分）|
| work_time_s | 📡 (2802) | 累计工作时间，维护触发用 |
| created_at, retired_at, is_active | 系统 | |

### 5.2 run（运行记录·主表）—— 自动开/关，元数据补录
| 字段 | 来源 | 说明 |
|---|---|---|
| id, device_id, channel | 系统/📡 | |
| started_at, ended_at, duration_s | 🧮 | run 检测器自动填 |
| end_status | 🧮 | completed / manual_abort / alarm_abort / unknown |
| **operator, project_tag, experiment_tag, remark, tagged** | ✍️ **补录** | 跑完后人工补；tagged=false 表示待补录 |
| work_mode, target_volume(+unit), inject_rate, aspirate_rate, pause_delay_s, repeat_count, prewarn_pct | 📡 | run 开始时从遥测读设定 |
| continuous_control(脉冲/电平), continuous_direction | 📡 | 连续模式补 |
| syringe_vendor, syringe_spec, syringe_inner_diam (或 Custom 值) | 📡/✍️ | 泵专有 |
| result_acc_volume(+unit), alarm_count | 📡/🧮 | run 结束时汇总 |

### 5.3 sample（采样序列）
id, run_id, device_id, ts, state, flow_rate, delivered_volume, temp_c, **metrics_json**（类型特有扩展，如搅拌器转速/温度、粘度计剪切/扭矩）—— 全部 📡 自动。

### 5.4 event（事件流）
id, device_id, run_id(可空), ts, **event_type**, severity(info/warning/critical), detail_json。
- type：start / stop / pause / resume / **stall_alarm**（堵车，机械保护，critical）/ alarm_clear / comms_lost / comms_recover。
- 事件由 RunDetector 在状态转换时自动产生（见 §6.1）。

### 5.5 calibration（校正台账）—— 人工表单
id, device_id, calibrated_at, operator, syringe_vendor/spec/inner_diam, **test1/test2/test3**(称量值), avg_volume, old_coeff, new_coeff, param_coeff, note。
- 当前系数(4035)、自定义注射器内径/规格(4088/4090) 📡 可预填；称量值 ✍️；新系数可按手册公式算或读泵算好的。

### 5.6 maintenance（维护/故障记录）—— 人工表单
id, device_id, kind(maintenance/fault), performed_at, operator, maintenance_type, **parts_replaced**(JSON：[{部件, 备件号}]), fault_phenomenon, troubleshooting, resolution。
- 备件号来自手册（注射器、保险管 1A、电源线 250V10A 等）；故障对照手册 9 类故障表。

## 6. 关键流程

### 6.1 Run 自动检测 + 事件（核心，无需写控制）
RunDetector 消费每台设备的 `StatusSnapshot` 流，按状态转换开/关 run 并发事件：
```
IDLE(state=stopped):
  →running : OPEN run(started_at=now, 读设定, tagged=false); 事件 start
RUN OPEN(running/paused/alarm):
  →paused  : 事件 pause
  paused→running : 事件 resume
  →alarm(堵车 1047+1980) : 事件 stall_alarm(critical→飞书); run.had_alarm=true
  alarm→正常 : 事件 alarm_clear
  →stopped : CLOSE run(ended_at, duration, end_status=had_alarm?alarm_abort:completed,
                        result_acc_volume=末值, alarm_count); 事件 stop
  通讯断(offline) : 事件 comms_lost(critical→飞书); run 保持开; 恢复发 comms_recover
```
→ 即便不控制设备，也能完整记录每次运行 + 事件时间线。

### 6.2 补录（tagging）
UI「待补录」列表展示 `tagged=false` 的已结束 run；操作员选中后补 operator/project_tag/experiment_tag/remark → `tagged=true`。超过 N 小时未补录的标黄提醒。

### 6.3 校正录入
表单：选设备/注射器 → 预填当前系数(4035)与自定义注射器参数(4088/4090) → 录入天平 test1/2/3 → 算平均/新系数（手册公式）→ 存 calibration 表。系数趋势图按注射器聚合，漂移超阈或超周期提示重校。

### 6.4 维护录入 + 提醒
- 录入：维护/故障表单（部件下拉带备件号）。
- 提醒规则（按设备类型，编码自手册维护作业表）：
  - 累计工时触发：丝杆/导杆润滑（每 X 工时）。
  - 日历触发：注射器至少每 3 天检查；轴承每年检查。
  - 数据源：device.work_time_s(2802，周期性采样入库) + 维护表上次时间。

### 6.5 飞书告警
critical 事件（stall_alarm / comms_lost）→ POST 飞书机器人 webhook，消息含：哪台设备、哪个通道、当时在跑的 run（项目/操作员，若已补录）、事件详情。webhook URL 在 config。

### 6.6 导出
- **run 汇总表**（一次一行）：run 表字段，按筛选批量。
- **采样明细**（画图用）：选中 run 的 sample 序列。
- 格式：CSV（分析）、Excel（多 sheet）、PDF（存档/审计，格式化报告）。
- 筛选维度：设备 / 操作人 / 项目 / 时间段 / 注射器规格。

## 7. 功能清单

1. **实时看板**：每台/每通道一张卡，状态色（红停/绿运行/绿闪暂停/红闪报警）、进度、剩余时间、瞬时流速/转速/粘度。
2. **运行记录查询**：列表+筛选+搜索；点单条看流速曲线 + 事件时间线。
3. **导出**：CSV/Excel/PDF；汇总+明细两档；按筛选批量。
4. **校正管理**：系数历史趋势 + 漂移/周期重校提醒。
5. **维护管理**：维护/故障记录 + 维护提醒（工时+日历双触发）。
6. **异常告警**：堵车/通讯断实时推飞书。
7. **利用率统计**：设备/人/项目三维的时长、次数、吞吐液量。

## 9. 决策记录（已确认 2026-07-01）

1. 数据库：**SQLite**。
2. 多设备：✅（泵×1、粘度计×1、搅拌器×5；schema 多设备就绪）。
3. 操作人/项目：**事后补录**（设备物理动作先于电脑，预填会因时钟不同步漏数据）。
4. 校正 & 维护：人工录入表单，**接入系统**。
5. 告警：**飞书机器人 webhook**。
6. phase-2 写控制：**本期不做**（Slice E）。

## 10. 复用与待定

**复用**：phase-1 采集层（`InstrumentAdapter`/`sampler`/`StatusSnapshot`、`modbus_io`、各设备 adapter）。新增业务层 + DB + UI。

**待定/后续确认**：
- 泵：序列号/固件版本是否有可读寄存器（否则人工填）；状态推导已在真机校准（stopped 正确），running/alarm/paused 待运行态验证。
- 粘度计：自定义协议的校验和/扭矩换算/第二帧类型，待 `viscometer_capture.py` 抓帧确认。
- 搅拌器(×5)：串口参数待 `stirrer_probe.py` 探测；5 台 RS485 总线编址与分组（接组网方案的串口服务器口）。
- 多设备接入：`TcpTransport` + 多设备并行（接组网方案）。
- 注射器厂商/规格是否能从泵读出（4021 编号 + 手册内径表），还是部分人工——run 开始时自动抓取的边界待真机确认。
